# 作業別ガイド / Task-specific guidance

必要な節だけ読む。文書の日付付き作業枠やモデル名は、現在のユーザー指示を置き換えない。以下はモデルに依存しない作業条件。

## Anatomy and meshes

分節境界、模式配置、断面併設3Dを変更するときに使用する。

- 分節は原画像・隣接断・直交断とランドマークで判断する。暗さ、連結性、座標だけでは帰属を決めず、旧ID33を左右や座標だけで分割しない。外部背景へ開いた腔をflood-fillで埋めない。別標本のラベルは比較資料でありBigBrainへ直接転写しない。
- 教材として位置・形・つながりを理解できる概略分節を優先する（2026-09-19ユーザー指示）。ピクセル単位の完全一致や全サンプルの内部包含を採用条件にしない。原画像で大まかな範囲を追える場合は、部分体積と概略境界を明示してまとまった範囲を採用する。明らかな別組織・外部空間の混入は避け、帰属不明と細部の粗さを区別する。
- 不明な境界は根拠と不足情報を示して保留する。人への判断依頼は引きの位置図・原画像・現行／候補を並べて一件ずつ。独立して進められる作業は継続する。
- 模式モデルには文献に基づく概略配置を使える。標本由来分節とは明示的に区別し、見た目のために根糸や未収録構造を増やさない。境界規約が必要なら [判断資料](FIBER_BOUNDARY_METHODS_2026-09-16.md) を使う。
- 差分は既存形式を再利用し、入力／出力SHA、可逆差分、採否理由を残す。ブラウザ編集・差分形式・validator・寄稿者のレビュー手順は [共同制作フロー](SEGMENTATION_WORKFLOW.md)。検証通過、プロジェクト採用、専門家確認はそれぞれ別の状態。
- メッシュ修正は、まず表示が参照するラベル版・座標・左右・crop・解像度を照合する。ブロック用の片側切出しを全脳表示に流用しない。生成だけで新しい解剖境界が正しくなるわけではない。[全構造3Dの修正記録](SECTION_BILATERAL_MODELS_2026-09-16.md)。
- 採用する変更に応じ、断面・3D・関連ブロック・日英説明・ブラウザ参考文献を同期する。原画像・復元用データ・確認図は保持する。既存installerを古い入力で再適用しない。
- 分担が指示された場合は、結果、入力、編集範囲／禁止事項、検証、返却内容を限定して渡す。同じファイルやラベル本体を同時編集させず、主担当が採否と統合を管理する。

## Verification

- 検査を追加・実行する前に、今回起こり得る具体的な不具合と、その検査でしか得られない確認を決める。既存の生成時検証・差分確認・実画面で確認済みなら同じ目的の検査を重ねない。低リスクの文書変更は差分確認で終える。
- 小さな分節採用の区切りを、全体試験を行う「統合時」とは扱わない。ラベルのみの変更で型検査を繰り返さず、表示更新に必要なbuildはまとめて一度行う。対象の確認が通ったら次の教材改善へ進み、理由なく検査範囲を広げない。
- 過去の採用を証明する試験は当時の固定入力・出力を検証し、最新ラベルの点数・SHAを各履歴試験へ複製しない。現在の整合性は共有の検査に集約する。整理は次に該当試験を変更する機会に必要な範囲で行い、テスト体系の全面改修を教材改善より優先しない。
- 文言・CSSなど局所変更は対応する検査を行う。全件試験を変更ごとに繰り返さず、実装文字列だけをなぞる試験を増やさない。
- 分節作業中は、実際の変更voxelの可逆性・対象外への影響・対応する3Dと実画面を優先する。小さな採用ごとに全件試験や両形式buildを繰り返さない。型検査と対象試験は変更した挙動に絞り、Node／Python全体試験は複数変更をまとめる統合時または公開前に行う。全体試験で失敗しても、原因修正後はまず対象だけ再試験し、共通処理への影響がない限り全件を再実行しない。
- 検査のためだけの構造数・一覧・現在値の手動複製を増やさない。新しい構造の追加は既存の出典・表示・分節の対応で確認し、履歴を固定する証拠と現在値の検査を区別する。既存検査を整理する際は異常を検出する目的を維持し、単に成功させるために期待値を緩めない。
- 実行コマンドは [開発ガイド](DEVELOPMENT.md)。失敗・修正後の対象再試験・未実施の全体再試験を区別して記録する。試験件数より、何が確認できて何が残るかを報告する。
- ローカル原画像がないためのskipは画像確認成功ではない。長い全volume検査が無出力でも重複起動しない。ローカル表示更新は実際の配信ディレクトリと稼働を確認し、他タスクのプロセスを止めない。

## Publication

公開準備・公開障害調査のときに使用する。

- 正式な公開先は [GitHub Pages](https://bonnginn.github.io/brain-practical-navi/)。旧Sitesの状態から公開障害を判断しない。実際の配信手順は `.github/workflows/` を確認する。
- 公開指示が対象とする差分を最新mainと照合する。部分公開なら、独立したcheckoutで公開版のラベルから対応モデルを再生成するなど、未承認の開発差分を混入させない。開発checkoutのデータを公開版で上書きしない。
- 権利の判断は [LICENSES.md](../LICENSES.md)、[出典と変更履歴](../DATA_AND_LICENSES.md)、配布対象の `public/atlas/DATA-MANIFEST.json` と個別noticeを照合する。出典別の条件を一つの汎用ライセンスで置き換えない。フィードバックフォームは [開発ガイド](DEVELOPMENT.md#日英フィードバックフォーム) の公開URL境界を守る。
- 通常／Pages形式build、出典・配布検査、CIを確認してから、許可されたpush・main統合・配信を行う。公開指示をすでに得ていれば同じ操作の再承認は求めない。公開URLの挙動と配信資産を確認し、コミット・配信結果を再開メモへ記録する。

## Documentation

- READMEは短い日英利用案内を維持する。開発履歴は個別docsへ、再開メモは現在値・残件・参照先だけにする。日付付きの停止／承認／担当記録を常時指示へ戻さない。
- [文書索引](README.md) は作業別の入口から必要な個別記録だけを選ぶ。過去の一括読込を要求しない。
- 古い証拠がbasenameで文書を参照するときはルート、次に `docs/` を探す。ハッシュ固定文書はリネームや注釈追加でも検査を壊し得る。原本を保持し、索引・新しい案内側で歴史的な位置付けを説明する。
- 新しいrepo skillは、明確な反復作業と入力・完了条件があり、既存docsへのリンクより有益な場合だけ検討する。descriptionは「何を／いつ使うか」に絞り、詳細・分岐は本文または参照先へ置く。共有インストール済みskillsはこのrepoの文書整理で改変しない。
